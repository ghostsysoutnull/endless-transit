# Entropy & ProcGen Domain Lessons

## Patterns
- **Vertical vs. Horizontal Entropy**: Use `locus.branch(index)` for child location seeds (vertical, hierarchy-stable) and `locus.nextRandom()` for sequential attributes within a single location (horizontal, within-node variance). Mixing these causes seed drift.
- **Hierarchical Seed Scrambling**: Initialize a single `Random` (scrambler) from the parent seed and call `nextLong()` for each child's seed. Avoids the repetition pattern from linear seeding (`seed + index`).
- **Service Determinism**: All component engines (`NameGenerator`, `ThemeService`) must accept an explicit `LocusSeed`. Never use `new Random()` or `ThreadLocalRandom` inside utility methods — this introduces seed drift during parallel tests.
- **SeedScanner + WorldProbe Pattern**: Use the Specification Pattern (`WorldProbe.shouldEnter(Location)`) to prune subtrees during seed scans. Drastically reduces scan time versus full-universe traversal.
- **Scenario Discovery**: `SeedScanner` + `SeedVault` for horizontal exploration; `WorldGenesis.resolveLIP` for vertical restoration from a saved LIP string.

- **Measure variety per planet, not per list; a serial does not count**: the effective pool of any generated string is bounded by the slowest-varying input in its vibe chain — the timeline is drawn once per *planet* and two cultures per planet, so 8 × 8 items × 2 phrasings gives ≤ 256 objects for every room on the planet, whatever the list sizes look like in isolation. Three of a room's four description lines were a single string over large parts of the world because a missing resource file falls back silently (`ThemeService.groovy:85-93`); no test noticed, because `ProcgenVariabilityTest` counts *room names*, whose uniqueness is a hex serial (`NameGenerator.groovy:120`) — a suffix that keeps strings apart is not variety. Before growing a list, count distinct strings across a corridor, a floor and a planet with a scratch script (`docs/analysis/VARIETY_AUDIT.md`, Appendix A), fix the structural cap first, and add a pin that every key in each `index.txt` has its file so a fallback can never fire unseen. (HK-016 audit.)
- **Rehearse a content change in a classpath overlay before asking for authorization**: put the proposed resource files (and, if a loader must change, a copy of that one class compiled to the scratchpad) *ahead* of `src/main/resources` / `build/vinc` on a `groovy -cp`, run `HudFrameHarness.captureAll()` against the committed goldens and walk the pinned seed. The plan can then state the exact gate movement per commit instead of "expected none"; HK-016 step 1 predicted every commit correctly and the rehearsal itself found two defects reading had missed — the glitch branch asked for `"Abyssal"` while the file is `abyssal.txt` (case-sensitive `TreeMap`; every glitched room fell back), and a longer sentence exposed a pane-width bug (HK-017). The repo is never touched; the overlay dir is deleted with the scratchpad.
- **A glitch or fallback key is a resource key**: whatever string a branch feeds into a lookup (`"Singularity"`, `"abyssal"`) must be in the index with a file, same case, and the coverage pin must enumerate those keys explicitly (`ThemeResourceCoverageTest.GLITCH_STRUCTURE_KEYS`) — the indexes only know the keys the world rolls, not the ones a branch invents. (HK-016 step 1.)

## Mistakes/Corrections
- **Static Seed Pollution**: Static `Random` instances in utility classes cause tests to pass in isolation but fail in batch due to state leakage. Always instantiate a new `Random` with the provided seed per call.
- **Repetition Drift**: Siblings that look identical are caused by using `seed + index` instead of a scrambled `nextLong()` per child. Fix: use `HierarchicalSeedScrambling` pattern above.
- **Factory Ordering Sensitivity (corrected, Phase 9)**: `LocusSeed` is `@Immutable` and every draw (`nextInt`, `pickFrom`, `checkProbability`, …) is a pure function of `value` + a fixed branch key — the *order* of factory calls cannot shift entropy. What is order-sensitive is a `java.util.Random` obtained from `nextRandom()` and consumed across several calls (room furniture, apartment object pool). When moving factory bodies, keep each `Random`'s consumption inside the method that creates it, and pin the resulting lists (`ProcgenDeepSnapshotTest`) — `DeterministicUniverseTest` only proves two runs agree with each other.
- **A pure roll inside a loop is one roll**: `f.locus.nextInt(100) < 30` evaluated per child returns the same value every iteration, so the "30 % per child" comment is wrong — the whole filament is null or not (HK-007). When a per-iteration chance is intended, branch on the child locus (`childLocus.branch("KEY")`), never re-roll the parent.
